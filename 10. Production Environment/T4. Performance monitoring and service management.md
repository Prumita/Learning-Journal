## Why is reliability a feature?
What does reliable mean? For IT folks, if lights are green and nothing has crashed then that's okay.
Users don't care about that though, they expect that to be running. So they care about:
- Is data fresh?
- Is it fast?
- Is it right?

Sales pipeline runs every night, green every morning. Issue upstream sends empty file.
Technically still green, 0 rows load no problem, no failure.
End user then gets a dashboard saying 0, so they're either unhappy or misinformed.
So that example, server is up, but for end users that has failed. Reliability is measured in outcomes therefore, not just, is it up?
Did it arrive? at the right time? In the right shape?

## Error Budget
What you can afford to miss?
So target 99%? Accept that 1% of the time, it won't happen.
Means 3-4 days a year can expect it to not be refreshed by 9am and that's okay. That's the error budget that has been defined and agreed.
Why do that? Why is it useful? Changes the conversation. Still got budget left? Take some more risks, ship hew feature, do migration. If you're already over budget, that tells you it's time for something to change, focus more on stability and stop releasing new features.

## Burn rate
How fast are you spending that budget? Burn rate of 1 is on track to use exactly that budget by the end of the month. So if you're burning through at 14 times the normal rate, you'll go through it in a couple of days.

## Miller's law
A human retains about seven items, plus or minus two, in their working memory at one time.
Dashboard of more than 7 can be overwhelming to users.

## Dashboard design blueprint
A lot of dashboards don't look simple, 40 panels, everything you can think of. So then when something breaks no one knows where to look.
One dashboard, one story. Three layers. Top, middle, bottom.
Top layer is your outcomes, your SLIs.
Green, amber, red, easy.
Middle layer, explanations. Where is something going wrong? kafka consumer lag. How long is each task taking? queue depth? retries? Things that give explanations for the SLIs.
Bottom layer is the resources, might give why something could have happened. CPU, memory, disc, warehouse credits.
Good to read top down, like we do in real life.

## Spotting bottlenecks
Idea here, don't read one thing on it's own, read it together.
So got a chart, latency is going up, throughput increasing and then decreasing.
So if the lag is increasing, and CPU is high? Compute bottleneck. That means that the workers are running low or flat out and can't keep up. So you'd scale out, or make the transformation more efficient.
But if the lag is raising and CPU is still low. That's a different story, more of a downstream issue. Workers aren't busy, they're waiting. Database is slow to accept rights, API throttling you or table is locked.
Same symptom, lag is up, but totally different fix.
Example, say you have a spark, airflow or prefect(?). Made to handle large volumes of data so it's running slowly, so add more workers so you have more computational capabilities. It would cost you more money and the job would still take the same amount of time. CPU was already low, CPU wasn't the issue. Maybe issue was database at the end which couldn't write fast enough. Fixed the wrong bottleneck here, didn'tactually address the problem.

## Playbook 
A playbook is a checklist for when things go wrong. Under pressure people forget things.
Imagine there is some sort of consumer lag happening in a pipeline. Check the trend, is it increasing, flat or recovering? Might then go into checking all of the workers are live, or is there a group that's stuck. Then you might go into  'was there a deployment in the last couple of hours?' maybe roll it back if there was. Then maybe check CPU against downstream latency, things like that. Having things in place to help in case issues occur. 
Basically a procedure of where to look, what to do.

Import the above bits and bobs. Next extract data.

```
def extract_data(file_path: str) -> pd.DataFrame:
    print("Extracting data...")
    data = pd.read_csv(file_path)
    print(f"Extracted data with shape: {data.shape}")
    return data
```
Gonna use pd.read_csv to load data, then print and return data.

Then we start to weave in prefect, so we add an @task, tells prefect this is a task.

Next going to transform the data:
```
@task
def transform_data(data: pd.DataFrame) -> pd.DataFrame:
    print("Transforming data...")


    # Add 'year_month' column from 'order_date'
    data['order_date'] = pd.to_datetime(data['order_date'], dayfirst=True)
    data['year_month'] = data['order_date'].dt.to_period('M').astype(str)


    # Calculate total revenue per customer
    total_revenue_per_customer = data.groupby('customer_id')['total_amount'].sum().reset_index()
    total_revenue_per_customer.columns = ['customer_id', 'total_revenue']


    # Merge revenue data back to original DataFrame
    data = data.merge(total_revenue_per_customer, on='customer_id')


    # Filter orders with total_amount > 100
    data = data[data['total_amount'] > 100]


    print(f"Transformed data shape: {data.shape}")
    return data
```

So doing the transofmr here, going to extract and then trasnform.
```    
@task
def load_data(data: pd.DataFrame, output_path: str):
    print("Loading data...")
    data.to_csv(output_path, index=False)
    print(f"Data successfully saved to {output_path}")
```
Lastly we have load. So we've set the tasks using the prefect task. Now we use flow. So pasting the flow in.

```
    # Flow: Orchestrate the tasks
@flow
def etl_pipeline(file_path: str, output_path: str):
    raw_data = extract_data(file_path)
    transformed_data = transform_data(raw_data)
    load_data(transformed_data, output_path)


# Execute the workflow
file_path = "orders.csv"  # Input file path
output_path = "transformed_orders.csv"  # Output file path


etl_pipeline(file_path, output_path)
```
This is the flow. First gonna extract the data. Then trasnform the data which we defined. Then it's gonna do the load which we defined.
Then gonna execute that workflow. Gonna point to the orders.csv file. Put it in the downloads. So that uploads and then things happen.
